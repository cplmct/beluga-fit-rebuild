Implement the approved password-recovery hardening patch for Beluga Fit.

This is an implementation task, but keep the scope narrow.

- Change Supabase Dashboard settings.
- Change database schema, migrations, RLS, RPCs, or delete_user.
- Change app.json, app.config.js, eas.json, package versions, or Metro configuration.
- Install dependencies.

- Commit or push.

Existing confirmed findings:
- parseRecoveryUrl() accepts any string beginning with the belugafit prefix rather than the exact reset route.
- Invalid, expired, and error-only recovery links can fail silently.
- Malformed URL decoding can reject without controlled UI feedback.
- Thrown reset-request or password-update errors can leave a form loading indefinitely.
- Recovery mode is a global boolean and can survive an ordinary account-owner change.
- Password recovery/update can proceed while a pending local account-cleanup marker exists.

Required behavior:

1. Exact recovery-route validation
- Accept only the intended custom-scheme reset destination:
  belugafit://reset-password
- Parse the URL structurally, not with startsWith().
- Reject:
  - other schemes,
  - scheme-prefix lookalikes,
  - wrong routes,
  - unrelated same-scheme routes,
  - malformed URLs.
- Preserve the currently supported fragment-token and query-token formats only if they are valid for the exact reset route.
- Decide and document fragment/query precedence.
- Catch malformed percent encoding and return a controlled invalid result instead of throwing.
- Do not log access_token or refresh_token values.

2. User-visible recovery-link state
- Add explicit recovery-link status in AuthContext, such as:
  idle, processing, invalid, expired, failed, or ready.
- Store only a safe user-facing error message; never store tokens in UI state.
- When a recovery link is invalid, expired, error-only, or rejected by setSession():
  - do not silently ignore it,
  - leave the user in a controlled recovery/error state,
  - show a safe explanation,
  - provide a request-another-link action that returns to the reset-request flow.
- Handle cold-start and warm-start link-handler failures with catch/finally.
- Do not leave the app indefinitely loading because URL parsing or session import failed.

3. Loading cleanup
- Add try/catch/finally to ForgotPasswordScreen reset requests.
- Add try/catch/finally to ChangePasswordScreen password updates.
- Preserve returned Supabase errors.
- Convert thrown exceptions into safe visible messages.
- Ensure controls re-enable after returned errors, thrown errors, malformed links, and account-change rejection.
- Apply the same safety behavior to ResetPasswordScreen if it remains in source, even though it is not currently routed.

4. Bind recovery mode to an account
- Replace the global recovery boolean behavior with owner-bound recovery state, for example:
  recoveryOwnerId: string | null
- Set it only after the recovery session is successfully established.
- Clear it when:
  - password update succeeds,
  - the user cancels recovery,
  - a recovery link fails,
  - the active owner changes to another account,
  - sign-out completes.
- Preserve it across same-owner token refreshes.
- If Account B’s recovery link replaces Account A’s session, ensure all account-scoped state reflects B before showing the recovery form.
- Do not allow recovery mode for one owner to remain attached to a later owner.

5. Pending-cleanup interaction
- A pending local cleanup marker must block password recovery/update mutations for that owner unless the design explicitly completes or clears cleanup first.
- Recovery-link handling must not bypass cleanup or account-transition protections.
- If recovery is blocked by pending cleanup, show a safe actionable message rather than silently dropping the link.
- Preserve the existing Account A/Account B draft isolation behavior.

6. Recovery controls
- Add a visible “Request another reset link” action for invalid/expired/failed recovery.
- Add a safe cancel/back action that exits recovery without exposing another account’s data.
- Keep the existing successful-password-update navigation behavior unless a small acknowledgement is required to ensure success is visible.

7. Tests
Add focused tests without new dependencies:
- Exact valid reset route with fragment credentials is accepted.
- Exact valid reset route with query credentials is accepted if intentionally supported.
- Wrong route is rejected.
- Wrong scheme is rejected.
- Scheme-prefix lookalike is rejected.
- Same-scheme unrelated route is rejected.
- Malformed percent encoding returns a controlled invalid result.
- Missing type/access token/refresh token is rejected.
- Error-only callback produces visible recovery error state.
- Code-only callback is handled deliberately as unsupported, with visible guidance.
- Expired/rejected setSession produces visible recovery error state.
- Thrown reset-request error releases loading.
- Thrown password-update error releases loading.
- Recovery owner B does not remain active after an ordinary session change to C.
- Same-owner token refresh preserves recovery mode.
- Pending cleanup blocks recovery/password update with visible feedback.
- Account A/B isolation remains passing.
- Logout and cleanup overlay tests remain passing.
